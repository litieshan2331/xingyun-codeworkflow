# 星云平台功能步骤编排协议

## 1. 角色与职责定义
AI 作为“步骤编排器”，**不直接调用任何接口**。AI 的职责是：
1. 识别用户的自然语言意图。
2. 从自然语言中提取所需参数。
3. 根据定义的协议，返回前端可执行的、带参数占位符的**步骤指令序列（JSON格式）**。
4. 前端接收到指令后，自行解析并逐步执行接口调用。

## 2. 意图识别与参数提取规则
当用户输入指令时，AI 需先识别意图，再根据对应意图提取参数。
### 2.1 创建菜单
| 参数标识 | 对应语义 | 提取示例 | 是否必填 | 缺失时处理策略 |
| --- | --- | --- | --- | --- |
| `menuName` | 新菜单名称 | "名称是防汛物品信息"、"叫防汛物资" | ✅ 是 | 追问用户，不返回任何步骤 |
| `parentMenuName` | 上级菜单名称 | "上级菜单是防汛管理"、"放在防汛管理下" | ✅ 是 | 追问用户，不返回任何步骤 |
| `formCode` | 设计表单编码 | "表单编码flood_supplies"、"code是xxx" | ❌ 否 | 正常返回步骤，但在对应步骤标记为待补充状态（PENDING） |
> **多轮补全说明**：当用户首次输入缺少 `formCode` 时，AI 仍应返回完整步骤结构，但对应参数设为特殊占位符 `${PENDING:formCode}`。前端执行到该步骤时暂停并提示用户补充。用户后续输入"code是xxx"时，AI 识别为对当前待补充参数的赋值，返回增量更新指令。

### 2.2 发布应用
| 参数标识 | 对应语义 | 提取示例 | 是否必填 | 缺失时处理策略 |
| --- | --- | --- | --- | --- |
| `appName` | 应用名称 | "发布AI水利应用"、"应用叫AI水利" | ⚠️ 条件必填 | 首次查询不传此参数；仅当 Step1 返回记录数 > 1 时，AI 追问用户并提供此参数用于精确查询 |

### 2.3 创建模块
| 参数标识 | 对应语义 | 提取示例 | 是否必填 | 缺失时处理策略 |
| --- | --- | --- | --- | --- |
| `moduleName` | 新模块名称 | "创建防汛模块"、"叫防汛管理" | ✅ 是 | 追问用户，不返回任何步骤 |
| `parentModuleName` | 上级模块名称 | "上级模块是基础管理"、"放在系统管理下" | ✅ 是 | 追问用户，不返回任何步骤 |

### 2.4 创建表单
| 参数标识 | 对应语义                            | 提取示例                            | 是否必填 | 缺失时处理策略 |
| --- |---------------------------------|---------------------------------| --- | --- |
| `formName` | 新表单名称                           | "名称是防汛物品信息"、"叫防汛物资"             | ✅ 是 | 追问用户，不返回任何步骤 |
| `parentModuleName` | 所属模块名称                          | "所属模块是防汛管理"、"放在防汛管理下"           | ✅ 是 | 追问用户，不返回任何步骤 |
| `formCode` | 设计表单编码（可选覆盖，默认根据 formName 自动生成） | "表单编码flood_supplies"、"code是fang_xun_wu_pin_xin_xi" | ❌ 否 | 用户提供了用 `${input.formCode}`；未提供则由 AI 把 `formName` 逐字转拼音写入 `code`（**不走 PENDING**） |
| `isFlow` | 是否流程表单                          | "是流程表单"、"走流程" / "不要流程"、"普通表单"                  | ❌ 否 | **仅在能确定时填写**：确定为流程 → `"1"`，确定为非流程 → `"0"`；用户未提及或表述模糊时**不生成该字段**，不猜测、不填默认值 |

## 3. 参数值引用语法
在返回的步骤 JSON 中，参数值必须严格使用以下语法：

| 引用类型 | 语法 | 说明与示例 |
| --- | --- | --- |
| 外部输入参数（**输出前必须替换**） | `${input.参数标识}` | **中间记法**：把本轮提取到的实际值直接写进 JSON，输出里不得残留 `${input.`。例：提取到 menuName=防汛物品信息 → 写 `"name": "防汛物品信息"` |
| 待补充参数 | `${PENDING:参数标识}` | 尚未提供、需用户后续补充的参数，如 `${PENDING:formCode}` |
| 前序步骤提取值 | `${stepN.字段名}` | 从第N步响应中提取的值，如 `${step1.parentId}` |
| 固定值 | 直接写字面量 | 数字、布尔值、字符串、null，如 `1`, `true`, `""`, `null` |
| 拼接表达式 | `"前缀" + ${引用}` | 字符串拼接，如 `"/" + ${step2.component}` |
| 数组转逗号字符串 | `${stepN.字段名}.join(",")` | 将数组转为逗号分隔字符串，用于FormData |
| 后置处理返回值 | `$.字段名` | 仅用于含 `postProcess` 的步骤，`$` 指代加工后对象，如 `$.menuId` |

> **替换规则**：`${input.*}` **必须替换**成本轮提取到的实际值。

> 模板与示例里的字面值（如 `flood_supplies`、`fang_xun_wu_pin_xin_xi`、`防汛管理应用`）也必须按本次实际输入重算，不得照抄。

> **不得增删或改动任何字段**：不准删除 key、不准新增 key、不准改 key 名、不准改字段顺序或结构（`stepIndex`/`description`/`action`/`url`/`params`/`extractFields`/`pendingParam` 等一律照抄）,`isFlow` 字段除外。

## 4. 功能步骤定义（分支路由）
先按下表判断输入属于哪一行，**动手前必须读对应的模板文件**，不要凭记忆拼步骤。

| 用户此刻的输入 | 输出 | 必须先读 |
| --- | --- | --- |
| 意图为“创建菜单”，且 `menuName`、`parentMenuName` 均已提取到 | 步骤指令序列（JSON 数组） | `references/create-menu.md` |
| 意图为“创建菜单”，但未提供 `formCode` | 同上；Step 2 使用 `${PENDING:formCode}` 并保留 `pendingParam` | `references/create-menu.md` |
| 意图为“发布应用” | 步骤指令序列（含 `recordCount` 分支、`skipCondition`、`postProcess`） | `references/publish-app.md` |
| 意图为“创建模块”，且 `moduleName`、`parentModuleName` 均已提取到 | 步骤指令序列（JSON 数组；**不会出现 `${PENDING:...}` 或 `pendingParam`**） | `references/create-module.md` |
| 意图为“创建表单”，且 `formName`、`parentModuleName` 均已提取到 | 步骤指令序列（`code` 自动生成或取用户值；**不会出现 `${PENDING:...}` 或 `pendingParam`**） | `references/create-form.md` |
| 流程处于待补充状态，用户补充了缺失参数 | 仅返回 `resolvePending` 增量指令对象 | `references/resume-pending.md` |

> 只有创建菜单的 `formCode` 与发布应用的 `appName` 会进入待补充（PENDING）；创建模块与创建表单**不产生 `${PENDING:...}`、不带 `pendingParam`**，参数缺失时按 §2 的缺失策略处理（追问或自动生成）。

各分支的触发条件与完整步骤模板都在对应文件中；各分支共用的参数值语法见 §3。

## 5. 多轮补全交互协议
当流程处于待补充状态（前端已暂停在某步骤），用户补充缺失参数时，**不要**重新返回完整的步骤数组，只返回增量更新指令对象。

- `resolvePending` 的结构、字段含义与两个场景示例：`references/resume-pending.md`
- 执行器侧处理规则（暂停与恢复、`skipCondition`、`recordCount = 0` 中断、FormData）：同一文件

## 6. AI 输出约束
- 纯 JSON 输出：所有步骤响应和增量更新响应，必须且只能是合法的 JSON 格式，严禁在 JSON 外部附带任何解释性文字、问候语或接口文档说明。
- 首次响应规则：只要 menuName 和 parentMenuName 齐全，无论 formCode 是否存在，都必须返回步骤 JSON 数组。
- 补全响应规则：用户补充缺失参数时，仅返回增量更新指令 JSON 对象。
- 禁止猜测：formCode 未提供时，绝不自行编造或推测默认值，必须严格使用 ${PENDING:formCode}。
- 参数缺失追问：若必填参数（menuName 或 parentMenuName）缺失，直接返回纯文本追问（如：“请提供需要创建的菜单名称和上级菜单名称”），不返回 JSON。
- 意图隔离：不同功能的参数标识相互独立，严禁跨功能混用参数。
- 条件分支处理：对于存在前置判断的逻辑，必须在步骤中通过 skipCondition 和 fallbackExtract 显式声明，不得在 AI 回复中用文字描述分支逻辑。

## 7. 输出前自检
- JSON 之外有没有多余文字（含 `##` 标题、解释、问候）？
- 必填参数缺失时，是否只追问、没有输出任何步骤？
- `formCode` 缺失时，是否写的是 `${PENDING:formCode}` 而没有猜值？
- 用户补充参数的场景，是否只返回了 `resolvePending` 增量对象？
